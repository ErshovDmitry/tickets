# Использование

Команды `ticket` на каждый день и формат файлов тикетов, которые он создаёт.

## Команды

Быстрый старт:

```bash
# создать тикет (статус open), печатает путь к файлу
ticket new "Поломка экспорта" -t BUG -p high -d "Падает на больших файлах" -w ivan

# длинные детали: из файла (@путь) или из stdin (-); содержимое переносится байт в байт
ticket new "Поломка экспорта" -d @details.md
ticket new "Поломка экспорта" -d -

# -P переопределяет проект (по умолчанию = basename родителя tickets/);
# предупреждение в stderr, если имя проекта встречается впервые
ticket new "Чужой проект" -P otherproj

# список тикетов: по умолчанию active (= open + wip)
ticket list
ticket list all        # включая done/closed (только основной каталог — удалённые скрыты)
ticket list archive    # только архив
ticket list deleted    # только мягко удалённые
ticket list all -P otherproj   # фильтр по проекту (точное совпадение, регистр важен)
ticket list --type BUG          # фильтр по типу (точное совпадение, регистр важен)
ticket list --priority high     # фильтр по приоритету (точное совпадение, регистр важен)

# показать тикет (ищет и в архиве, и в deleted/)
ticket show 7

# сменить статус: open → wip → done / closed
ticket set 7 wip "взял в работу"
ticket set 7 done "починено, тесты зелёные"

# правка метаданных на месте: только --title/--type/--priority/--project (длинные флаги, раздельная форма);
# каждое изменённое поле даёт свою журнальную строку; успех тихий (код 0)
ticket edit 7 --title "Экспорт падает на огромных файлах" --priority normal

# перенести закрытые тикеты (done/closed) в tickets/archive/
ticket archive         # все закрытые
ticket archive 7       # один указанный

# мягко удалить тикет в tickets/deleted/ (терминальный, read-only); без --yes спросит yes/no
ticket delete 7 --yes

# разрешить пару файлов после прерывания смены статуса
# (номер отвечает кодом 2: T-0007-open.md + T-0007-done.md)
ticket recover 7 T-0007-done.md

# версия бинарника (dev, если собран без -ldflags)
ticket version
```

Предупреждения разбора печатаются в stderr; команда возвращает код выхода 0 и показывает успешно распарсенные тикеты.

Переменные окружения (`TICKETS_DIR`, `TICKET_WHO`, `TICKET_LANG`, `TICKET_LOCK_TIMEOUT`, `TICKET_LOG`) и глобальный флаг `-C`/`--tickets-dir`: [configuration.md](configuration.md).

### Ввод деталей (`-d`)

- Обычный текст — используется буквально.
- `@<файл>` — содержимое этого файла; содержимое переносится байт в байт (без обрезки, без конвертации переводов строк, без ограничения размера — больше 64 КиБ принимается).
- `@@имя` — файл с именем `@имя`: снимается ровно один маркер `@`, `@@` не является экранированием.
- `@` без пути — ошибка: путь после `@` обязателен.
- `-` — содержимое stdin.
- Пустой файл или пустой stdin — пустое значение `Details`; команда завершается успешно, а в созданном тикете показывается блок-формат `Details` (то же, что при `-d ""`).
- Отсутствующий файл или ошибка чтения stdin — ошибка: сообщение локализовано (ошибка файла называет путь), тикет не создаётся.

### Ввод комментария (`set`)

`ticket set <номер> <статус> ["комментарий"]` берёт комментарий из аргументов после статуса:

- ОДИН аргумент комментария — это источник, а не литерал: `-` — stdin, `@<файл>` — содержимое этого файла, `@@имя` — файл с именем `@имя` (снимается ровно один `@`, `@@` не является экранированием). Любой другой одиночный аргумент используется буквально.
- `@` без пути как ОДИН аргумент комментария — ошибка (код 1): путь после `@` обязателен. Диагностики используют формулировки `new -d` («детали из файла»), это те же сообщения.
- Содержимое переносится байт в байт, и срезается ровно один завершающий LF или CRLF — поэтому файл, записанный через `echo` (один завершающий перевод строки), принимается. Любой другой CR или LF — второй завершающий LF (`x\n\n`), одиночный завершающий CR (`x\r`), перевод строки внутри текста — отклоняется (код 1): имя тикета, его байты и журнал не меняются.
- Пустой файл или пустой stdin — пустой комментарий: смена статуса работает, а повторный `set` в тот же статус падает, как и без комментария (код 1).
- НОЛЬ аргументов комментария — комментарий пустой (повторный `set` в тот же статус без комментария — ошибка, как и раньше).
- ДВА или больше аргументов комментария — соединяются одним пробелом и берутся буквально: ни файл не читается, ни stdin не затрагивается, поэтому флагоподобное слово (`-x`) остаётся литералом.
- Компромисс: одиночный `-` или `@...` никогда не будет буквальным комментарием, а два аргумента — не побайтовый выход (пробел вставляется). `-` на терминале читает stdin до EOF (Ctrl-D).

### Фильтры list (`--type`, `--priority`)

`--type` и `--priority` сужают выборку и соединяются со статусом и `-P` по И:

```bash
ticket list --type BUG                              # только BUG
ticket list --priority high                         # только high
ticket list open --type BUG --priority high -P proj # статус И тип И приоритет И проект
```

- Значения точные, регистр важен: `--type` принимает `BUG`, `OPS`, `TD`, `ENH`; `--priority` — `low`, `normal`, `high`.
- Каждый флаг берёт значением СЛЕДУЮЩИЙ токен, даже если он похож на статус или флаг: `--type open` — это неверный тип, а не фильтр по статусу.
- Неверное значение — ошибка (код 1): `ticket list --type BUGX` печатает в stderr `ticket: тип — один из: BUG OPS TD ENH`.
- Пустой результат — не ошибка: обычный вывод печатает `Нет тикетов (active --type BUG).`, а `--json` — `[]`; код выхода в обоих случаях 0.
- `archive` выбирает архив источником; фильтр по статусу там не применяется, а `--type`, `--priority` и `-P` применяются.
- `deleted` выбирает `tickets/deleted/` источником по тем же правилам И: `--type`, `--priority` и `-P` применяются, фильтр по статусу — нет. Все прочие режимы статуса — `active`, `open`, `wip`, `done`, `closed`, `archive` и `all` — удалённые тикеты СКРЫВАЮТ: `all` сохраняет прежний смысл (основной каталог) и не расширяется.

## Пример вывода list

Пример вывода `ticket list all` — колонка проекта появляется, когда проекты в выводе различаются:

```text
T-0001  tmp         open     BUG: Экспорт падает
T-0002  tmp         open     ENH: Broken export
T-0003  otherproj   open     BUG: Cross proj
```

С фильтром `-P` колонка проекта исчезает (проект один):

```text
T-0003  open     BUG: Cross proj
```

`ticket list deleted` печатает удалённые тикеты так же, со статусом `deleted` в колонке статуса. Дубликаты номеров внутри `tickets/deleted/` участвуют в том же предупреждении о дубликатах (stderr, код выхода 0), что и везде; `show` на таком номере отвечает кодом 2.

## Чтение одного тикета (`show --section`, `show --json`)

`ticket show <номер|имя-файла> [--section <имя>] [--json]` имеет три взаимоисключающих режима вывода. Обычная форма не изменилась: файл тикета печатается побайтово в stdout, лишние аргументы остаются предупреждением в stderr (код 0). Отдельный токен `--section` или `--json` включает новый режим, и там флаги проверяются строго ДО чтения тикета: неизвестный флаг, повтор флага, склеенная форма `--section=<имя>`, лишние позиционные аргументы и сочетание `--section`+`--json` — это ошибки в stderr с кодом 1 и пустым stdout.

`--section <имя>` печатает только ТЕЛО секции — без строки заголовка `##` — и ровно один LF после него:

- канонические имена: `summary`, `details`, `user-comments`, `comments`, `journal`;
- алиасы: `brief` (= `summary`) и `user_comments` (= `user-comments`); имя регистронезависимо, окружающие пробелы отбрасываются, внутренние пробелы НЕ нормализуются (`user comments` отвергается);
- известная, но пустая секция — как и секция, которой в старом тикете нет вовсе, — это успех: код 0 и пустой stdout (0 байт);
- неизвестное имя — ошибка в stderr с кодом 1, в сообщении перечислены канонические имена.

Payload — это тело, сохранённое парсером, поэтому он языконезависим: `## Summary (Кратко)`, `## Summary` и `## Summary (<произвольный суффикс>)` дают один и тот же текст. Summary хранится отдельно от Details, поэтому `summary` — это тело секции Summary (не заголовок тикета). `journal` печатает строки журнала без разделяющих пустых строк.

`--json` печатает ОДИН JSON-документ в stdout — вся диагностика идёт в stderr, документ завершается ровно одним LF:

| Ключ | Значение |
|------|----------|
| `number`, `status`, `type`, `priority`, `project`, `title`, `who` | строки (number — число JSON) |
| `summary`, `details`, `user_comments`, `comments` | тела секций; присутствуют всегда, `""` когда пусто |
| `created` | RFC3339; `""` если исходную метку времени разобрать нельзя |
| `journal` | массив `{at, from, to, who, comment, archived}`, `at` в RFC3339 (`""` для неразбираемой метки); `[]` если журнала нет |
| `unknown` / `unknown_encoding` | ручной хвост после журнала: валидный UTF-8 отдаётся текстом с `"utf-8"`, всё остальное — base64 с `"base64"` (без потерь) |
| `warnings` | массив строк предупреждений парсера (`"<имя файла>: <ошибка>"`); `[]` если файл чистый |

Каждый ключ присутствует всегда (`omitempty` не используется), а статус всегда берётся из ИМЕНИ ФАЙЛА, а не из строки `- Статус:` в теле. Действует обычное HTML-экранирование `encoding/json` (`<`, `>`, `&` экранируются). Неизвестные секции `## ...` в головной зоне в JSON не выводятся: сохраняется только хвост в `unknown`.

## Запись текста (`comment`, `section set`)

```text
ticket comment <номер> [-] [--file <путь>] [--json] [--schema]
ticket section set <номер> <секция> [-] [--file <путь>] [--json]
```

Обе команды пишут текст тикета, не трогая статус и буллеты метаданных, и обе делят один контракт payload: источник — ровно один из `-` (stdin) или `--file <путь>`; нет источника или оба источника — ошибка использования (код 1), терминал не читается. Чтение и декодирование входа происходят ДО поиска тикета, поэтому отклонённый вход оставляет файл и журнал побайтово неизменными. После позиционных принимаются только раздельные пары `--флаг значение`; слитная форма `--флаг=значение` отклоняется.

- stdin — основной канал: heredoc в Unix (`ticket comment 42 - <<'EOF' … EOF`), конвейер в Windows (`type note.txt | ticket comment 42 -` в cmd, `Get-Content note.txt -Raw | ticket comment 42 -` в PowerShell).
- `--file <путь>` читает файл побайтово; завершающие CR/LF отбрасываются, остальные байты сохраняются как есть. Пустой файл читается как пустой payload.
- Строка payload — markdown-заголовок (1–6 `#`, затем пробел или конец строки) — отклоняется (код 1) с номером строки.
- `--json` трактует payload как строгий однополевой объект `{"text":"<payload>"}`: неизвестные поля — код 1 со списком полей/форматом/примером, невалидный JSON или мусор после объекта — код 1 с позицией/форматом/примером, без отката к plain. `comment --schema` печатает эту JSON Schema в stdout (код 0, без lookup и записи) и несовместим с источником (код 1).

`ticket comment` ДОПИСЫВАЕТ блок в секцию `Comments` — никогда не замена: ровно одна пустая строка отделяет новый блок от старого тела, журнал фиксирует дописывание (`comment: +N строк`, кто, когда). Пустой payload отклоняется (код 1).

`ticket section set` ЗАМЕНЯЕТ тело редактируемой секции целиком. `<секция>` — канонический CLI-токен: `summary`, `details`, `user-comments`, `comments`, `journal`, плюс алиасы `brief` (= `summary`) и `user_comments` (= `user-comments`); имя регистронезависимо, окружающие пробелы отбрасываются, внутренние пробелы не нормализуются. Редактируемые — `summary`, `details` и `comments`; защищённые — `user-comments` («Комментарии от пользователя») и `journal` («Журнал»): защищённое или неизвестное имя отклоняется (код 1) со списком редактируемых. Пустой payload очищает секцию (пустое краткое описание рендерится как заголовок).

Коды выхода обеих команд: `0` — тихий успех, parse-предупреждения в stderr; `1` — использование, I/O, защищённая секция, пустой комментарий, отказ из-за заголовка в payload, тикет в `tickets/deleted/` или отсутствующий тикет; `2` — неоднозначный номер, со всеми конфликтующими путями в stderr.

## Полная справка по командам

Полная справка по командам — текст `ticket help` (`TICKET_LANG=ru`), побайтово совпадает с встроенным шаблоном `internal/cli/templates/usage.ru.txt`. Бинарь печатает перед ним версионную строку (`ticket version <ver>`, `dev` если собран без `-ldflags`), которой в шаблоне нет:

```text
ticket — тикеты проекта (файлы T-NNNN-<status>.md в <проект>/tickets/).

  ticket init
      создать структуру тикетов: tickets/, tickets/archive/ и tickets/deleted/ (идемпотентно); учитывает -C/--tickets-dir и $TICKETS_DIR (по умолчанию: <текущий каталог>/tickets)
  ticket new "<кратко>" [-t BUG|OPS|TD|ENH] [-p low|normal|high] [-d "<подробности>"] [-w кто] [-P <проект>]
      создать тикет (статус open), печатает путь к файлу;
      -P переопределяет проект (по умолчанию = basename родителя tickets/);
      предупреждение в stderr если проект встречается впервые
      -d принимает детали: обычный текст — буквально, @<файл> — содержимое файла, @@имя — файл с именем "@имя", - — stdin;
      @ без пути — ошибка: тикет не создаётся, сообщение локализовано;
      содержимое переносится байт в байт, пустой файл или stdin — пустое значение Details: в тикете показывается блок-формат Details (то же, что при -d ""); ограничения на размер нет;
      формат Details — нумерованный список, по одному пункту на строку: N. <что> — <файл:строка>; <решение>
  ticket list [active|open|wip|done|closed|archive|deleted|all] [-P <проект>] [--type BUG|OPS|TD|ENH] [--priority low|normal|high] [--json]
      список тикетов; по умолчанию active (= open + wip);
      archive — закрытые тикеты, унесённые в архив;
      deleted — мягко удалённые тикеты в tickets/deleted/; все прочие режимы (active/open/wip/done/closed/archive/all) их скрывают, all по-прежнему только основной каталог;
      -P фильтрует по проекту (точное совпадение, регистр важен);
      --type/--priority фильтруют по типу и приоритету (точное совпадение, регистр важен), соединяются со статусом и -P по И;
      неверное значение --type/--priority — ошибка (код 1)
      колонка проекта отображается когда проекты в выводе различаются;
      --json выводит массив JSON (6 полей: number, status, type, priority, title, created); пусто = []
  ticket show <номер|имя-файла> [--section <имя>] [--json]
      показать тикет (ищет и в архиве, и в deleted/); неоднозначный номер — код 2 со всеми конфликтующими путями
      --section печатает только тело секции без заголовка (пустая/отсутствующая секция — код 0, пустой stdout; неизвестное имя — код 1)
      --json выводит один JSON-документ: number, status, type, priority, project, title, summary, created, who, details, user_comments, comments, journal[], unknown, unknown_encoding, warnings[]; статус берётся из имени файла
      режимы взаимоисключаемы; диагностика — только stderr; лишние позиционные аргументы — предупреждение (код 0) в plain и ошибка (код 1) в --section/--json
  ticket set <номер> <статус> ["комментарий"]
      сменить статус (сам переименует файл и допишет строку в журнал тикета);
      повторный set в тот же статус с комментарием допишет журнал
      (статус и имя файла не меняются), без комментария — ошибка;
      комментарий можно дать ОДНИМ аргументом: - — stdin, @<файл> — содержимое файла, @@имя — файл с именем "@имя";
      @ без пути как ОДИН аргумент комментария — ошибка (код 1), так же ошибка при отсутствующем файле и сбое чтения stdin — имя тикета, его байты и журнал не меняются;
      содержимое переносится байт в байт, и срезается ровно один завершающий LF или CRLF; любой другой CR или LF — второй завершающий LF, одиночный завершающий CR, перевод строки внутри текста — отклоняется (код 1), ничего не пишется;
      два или больше аргументов комментария соединяются пробелом и берутся буквально — ни файл, ни stdin не читаются;
      компромисс: одиночный "-" или "@..." никогда не будет буквальным комментарием, а два аргумента — не побайтовый выход (пробел вставляется);
      "-" читает stdin до конца ввода; на терминале ждёт EOF (Ctrl-D)
      перевод архивного тикета в open/wip возвращает его из архива в работу;
      deleted этим путём не назначается: явное имя статуса или тикет, чей файл лежит в deleted/, отклоняются — код 1, файл не меняется
  ticket edit <номер> [--title "<кратко>"] [--type BUG|OPS|TD|ENH] [--priority low|normal|high] [--project <проект>]
      правка краткого описания/типа/приоритета/проекта тикета на месте (статус и имя файла не меняются);
      архивный тикет правится в archive/ без возврата в работу, --project меняет только метаданные;
      только раздельные пары "--флаг значение": форма "--флаг=значение" и короткие флаги отклоняются; повтор — последнее значение;
      явно переданное неизменённое значение отклоняет всю правку (код 1, ничего не записывается); успех тихий (код 0);
      тикет, чей файл лежит в deleted/, отклоняется (код 1, ничего не записывается)
  ticket comment <номер> [-] [--file <путь>] [--json] [--schema]
      добавить текстовый блок в секцию «Комментарии» (никогда не замена); источник payload — ровно один из - (stdin) или --file <путь>;
      нет источника или оба источника — ошибка использования (код 1), терминал не читается; --file читается побайтово, пустой файл читается как пустой payload;
      --json трактует payload как строгий JSON {"text":"<payload>"} (единственное поле): неизвестные поля — код 1 со списком полей/форматом/примером, невалидный JSON или мусор после объекта — код 1 с позицией/форматом/примером, без отката к plain;
      --schema печатает JSON Schema в stdout (код 0, без lookup и записи) и несовместим с источником;
      только раздельные пары "--флаг значение" после позиционного номера; строка payload — markdown-заголовок (1-6 '#' затем пробел или конец строки) — отклоняется (код 1) с номером строки;
      пустой payload отклоняется (код 1); успех тихий (код 0), parse-предупреждения в stderr; тикет в deleted/ отклоняется, неоднозначный номер — код 2 со всеми конфликтующими путями
  ticket section set <номер> <секция> [-] [--file <путь>] [--json]
      заменить тело редактируемой секции; <секция> — канонический CLI-токен (защищённое или неизвестное имя отклоняется, код 1, со списком редактируемых имён);
      источник payload — ровно один из - (stdin) или --file <путь>; нет источника или оба — ошибка использования (код 1), терминал не читается;
      --file читается побайтово (пустой файл очищает секцию); --json трактует payload как строгий JSON {"text":"<payload>"} (единственное поле), неизвестные поля или невалидный JSON — код 1, без отката к plain;
      пустой payload очищает секцию (пустое краткое описание рендерится как заголовок); строка payload — markdown-заголовок — отклоняется (код 1) с номером строки;
      только раздельные пары "--флаг значение" после позиционных; успех тихий (код 0), parse-предупреждения в stderr;
      тикет в deleted/ отклоняется (код 1), неоднозначный номер — код 2 со всеми конфликтующими путями
  ticket archive [<номер>]
      перенести закрытые тикеты (done/closed) в archive/;
      без номера — все закрытые, с номером — один указанный;
      удалённые тикеты игнорируются: ни переносятся в архив, ни восстанавливаются из него
  ticket recover <номер> <файл-новый> [--yes]
      восстановить тикет после прерванной смены статуса, оставившей два файла на один номер;
      <файл-новый> — базовое имя файла, который сохраняется (например T-0001-done.md), не путь;
      без --yes печатает сохраняемый и удаляемый файлы и спрашивает yes/no;
      без --yes и без терминала отказывает и ничего не меняет;
      удаляется только устаревший старый файл, сохраняемый файл не перезаписывается;
      повторный запуск после успешного восстановления и единственный файл с выбранным именем — консервативный успех без изменений;
      recover лишь проверяет наличие нужного файла: он не может доказать, что это ранее сохранённый файл, а не одинокий устаревший,
      поэтому код 0 значит «нужное имя уже на диске», а не «восстановление произошло»
      код 2 — номер не восстановить однозначно (три файла и более, расходящееся содержимое, одинаковый статус в именах);
      выбор старого файла, файла вне пары или единственного файла с другим именем — код 1, дерево не меняется;
      пара после прерывания с участием deleted/ восстанавливается по тем же правилам — сохранить удалённый файл можно, выбор устаревшего источника по-прежнему код 1
  ticket delete <номер|имя-файла> [--yes] [--force]
      мягко удалить тикет в deleted/ (тело, метаданные и журнал сохраняются; добавляется одна строка журнала о переходе в deleted);
      <номер|имя-файла> — один ref: номер или точное базовое имя (например T-0001-open.md), не путь;
      без --force удаляется только open-тикет в основном каталоге; --force покрывает и прочие статусы основного каталога, и архив;
      без --yes печатает путь кандидата и спрашивает yes/no; без --yes и без терминала отказывает и ничего не меняет;
      --yes пропускает вопрос, но не обходит guard; дубликат номера или одинаковое базовое имя в нескольких каталогах — код 2 со всеми конфликтующими путями;
      точное базовое имя выбирает один файл из дубликата номера; уже удалён, конфликт цели или не найден — код 1, дерево не меняется;
      повтор после успешного удаления — код 1 (уже удалён), а не успех без изменений; успех печатает путь удалённого файла
  ticket normalize [-P <проект>] [--dry-run]
      разово привести формально устаревшие файлы к канонической разметке;
      переписываются только файлы, байты которых отличаются от канонических: имя и статус не меняются,
      журнал не дополняется (отдельной журнальной строки о миграции нет);
      -P ограничивает прогон одним проектом (точное совпадение, регистр важен);
      --dry-run печатает пути, которые были бы переписаны, и ничего не пишет;
      файлы, которые команда не берётся чинить, пропускаются с предупреждением (старые метки «- Статус:», неполные метаданные);
      удалённые тикеты тоже переписываются на месте (порядок обхода: main, затем archive, затем deleted)
  ticket update-check
      есть ли новый релиз на GitHub? (явная проверка; никогда автоматически); кэш на пользователя (24 ч), повтор не чаще чем раз в 1 ч; безопасна офлайн: сбой не блокирует другие команды

Глобальный флаг (перед командой, все команды):
  -C <путь>, --tickets-dir <путь>
      путь к самому каталогу тикетов (не к корню проекта); работает из любой текущей директории
  --verbose
      отладочный лог в stderr; TICKET_LOG=<путь> тоже включает лог и отправляет записи в этот файл (файл важнее флага);
      принимается только ДО имени команды; после help/version игнорируется; склеенная форма --verbose=x не распознаётся;
      stdout для записей лога никогда не используется; init игнорирует --verbose (логгер для init не создаётся)

Поиск каталога тикетов (первое совпадение выигрывает): -C/--tickets-dir → $TICKETS_DIR → восходящий поиск tickets/ от текущего каталога. Исключение: init использует <cwd>/tickets без восходящего поиска.

Блокировка каталога: TICKET_LOCK_TIMEOUT задаёт, сколько .lock может оставаться без признаков прогресса от держателя, прежде чем ticket вернёт ошибку (пока держатель работает, ожидание продлевается до 12× от заданного значения); значение — Go-длительность с обязательной единицей (30s, 2m, 500ms); пустое или невалидное значение молча даёт дефолт; 0 или меньше — одна попытка без ожидания; действует на new, set, edit и archive.

Коды выхода: 0 — успех; 1 — ошибка (неверные аргументы, тикет не найден, конфликт, ошибка ввода или хранилища, сбой проверки обновлений); 2 — неоднозначный номер тикета (команды show, set, edit, archive, new, recover, delete, comment, section): один номер принадлежит нескольким файлам — в stderr печатаются номер и конфликтующие файлы. Команда list при дубликатах печатает такое же предупреждение, но завершается с кодом 0; 3 — доступно обновление (команда update-check). Дубликаты номеров внутри `tickets/deleted/` подчиняются тем же правилам: `list` (в любом режиме) предупреждает и выходит с кодом 0, `show` выходит с кодом 2 со всеми конфликтующими путями, а `set`/`edit`/`comment`/`section` отказывают по удалённому тикету с кодом 1.

Статусы: open — новый; wip — в работе; done — исправлено; closed — отклонён/дубликат; deleted — мягко удалён (терминальный, read-only).
Типы: BUG — поломка; OPS — инцидент/обслуживание; TD — техдолг; ENH — улучшение.
Секреты (пароли, токены, ключи) в тикеты НЕ писать.
```

## Глобальные флаги

Распознаются два глобальных флага, и оба принимаются только ДО имени команды: `-C <dir>` / `--tickets-dir <dir>` (а также `--tickets-dir=<dir>` и склеенный `-C<dir>`) выбирает каталог тикетов для одного запуска, а `--verbose` включает отладочный лог.

`--verbose` пишет лог в stderr; если задан `TICKET_LOG` с путём, записи уходят в этот файл (файл важнее флага). stdout для записей лога никогда не используется. Токен, похожий на глобальный флаг, но стоящий ПОСЛЕ имени команды — это аргумент подкоманды, а не глобальный флаг: `ticket list --verbose` и `ticket new "T" -d x --verbose` — ошибки, а не тихие no-op. `--verbose` после `help`/`version` игнорируется, а склеенная форма `--verbose=x` не распознаётся.

```bash
ticket --verbose list                 # отладочный лог в stderr
ticket --verbose show 7 2>/dev/null   # лог всё равно в stderr, текст тикета остаётся в stdout
```

Формат записи, правила назначения, поведение при ошибках и полный список событий описаны в [configuration.md](configuration.md) — здесь они не дублируются.

## Правка метаданных (`edit`)

Правит метаданные существующего тикета на месте — только title, type, priority и project; статус и имя файла не меняются, Summary по умолчанию и Journal обновляются, остальные секции тела сохраняются:

```bash
ticket edit 7 --title "Новый заголовок" --type ENH --priority high --project otherproj
```

- Только четыре поля, только длинные флаги, только раздельная форма: `--title <заголовок>`, `--type BUG|OPS|TD|ENH`, `--priority low|normal|high`, `--project <проект>`. Склеенная форма `--title=значение` НЕ распознаётся, коротких флагов нет. Номер — первым; неизвестный флаг, пропущенное значение или лишний позиционный аргумент — код 1, как и вызов без единого поля.
- Значения валидируются до любой записи: неверный type или priority, заголовок или проект из одних пробелов, управляющие символы или начальный дефис в заголовке, CRLF в любом значении (инъекция в журнал) — код 1 без записи.
- Любое явно переданное значение, равное текущему, отклоняет ВСЮ операцию с кодом 1 и без записи — даже если остальные поля менялись бы. Успех тихий: код 0, stdout и stderr пусты.
- Каждое изменённое поле дописывает свою журнальную строку `<поле>: старое → новое` в фиксированном порядке title, type, priority, project, под одной меткой времени и одним автором; переход статуса в строке — текущий статус (From = To), поэтому значения со скобками round-trip'ятся.
- Смена заголовка переписывает H1; секция Summary обновляется, только если была пустой или всё ещё равна старому заголовку (значение по умолчанию) — кастомный Summary сохраняется.
- Статус и имя файла не меняются; архивный тикет правится на месте (без reopen и переноса). `--project` переписывает только метаданное поле — per-project каталогов не существует, ничего не перемещается.
- Запись идёт тем же in-place путём, что same-status у `set` (temp-файл в том же каталоге, затем rename); каталог `tickets/` только для чтения отклоняется. Неоднозначный номер ведёт себя как у `show`/`set`: оба конфликтующих абсолютных пути — в stderr, код 2.
- Тикет, чей файл лежит в `tickets/deleted/`, отклоняется до любой записи (код 1, файл не меняется): `deleted` терминален и read-only, `edit` не может его воскресить. Обратной операции (undelete) нет.

## Восстановление после прерывания (`recover`)

Смена статуса — многшаговый коммит: новый файл создаётся ссылкой, затем удаляются tmp и старый файл. Если процесс убит или упёрся в таймаут между шагами, остаются оба файла — например `T-0007-open.md` и `T-0007-done.md`. Номер становится неоднозначным: `show`, `set` и `archive` печатают оба конфликтующих АБСОЛЮТНЫХ пути в stderr и завершаются с кодом 2. Ровно для этой пары существует команда:

```bash
ticket recover <номер> <файл-новый> [--yes]
```

- `<файл-новый>` — имя файла из диагностики неоднозначности (например `T-0007-done.md`); каталог указывать не надо: basename сопоставляется с записями в `tickets/`, `tickets/archive/` и `tickets/deleted/` (пара после `reopen` или после прерванного `delete` тоже восстанавливается). Одинаковый basename в двух каталогах — отказ: путь не угадывается.
- Без `--yes` команда печатает, что остаётся (keep) и что будет удалено (discard), и спрашивает yes/no. Без терминала (не-TTY) и без `--yes` — код 1 и ни одного действия: пайплайн не может случайно удалить файл, автоматизация обязана передать `--yes`.
- Сигнатура распознаётся строго: новый файл = старый файл + РОВНО одна последняя запись журнала `From=старый статус → To=новый статус`, причём у старого файла такой завершающей записи нет. Сравнение идёт после разбора и рендера (все поля, включая unknown/RawTemplates): любое другое расхождение, лишняя или чужая запись журнала — отказ.
- Выбранное имя обязано быть новым файлом. Указан старый (keep old) — отказ с подсказкой: сначала `recover` нового, затем при необходимости `ticket set` в прежний статус.
- Удаляется ТОЛЬКО старый файл; новый не открывается на запись, его содержимое и журнал остаются байт в байт, tmp/ и запись о восстановлении не создаются.
- Повтор — консервативный no-op: если остался только новый файл, команда завершается с кодом 0 и ничего не меняет (файл не открывается на запись повторно). Тот же код 0 покрывает и единственный файл, уже названный `<файл-новый>` — постусловие здесь «нужное имя есть на диске», а не доказательство, что это ранее сохранённый файл.
- Откат статуса — обычный последующий `ticket set <номер> <прежний статус> "причина"`: он допишет журнал и переименует файл. Флага отката у `recover` нет.
- Пара после прерывания с участием `tickets/deleted/` восстанавливается по тому же правилу подписи: сохранить удалённый файл (`T-NNNN-deleted.md`) — успех, выбор устаревшего источника — обычный отказ keep-old (код 1). Восстановление такой пары ничего не «разделывает»: тикет остаётся терминальным.
- Любая ошибка оставляет пару на месте. Какие пути печатаются, зависит от диагностики: отчёт о неоднозначности (три файла и более, а также тот же отчёт из `show`/`set`/`archive`) перечисляет все конфликтующие АБСОЛЮТНЫЕ пути, а отказ `RecoveryState` называет только конфликтующие БАЗОВЫЕ ИМЕНА — при совпадении статусов путей нет вообще. Рассчитывать на пути в любой ошибке нельзя: повторять с базовым именем после устранения причины.

Коды выхода: 0 — успех, включая консервативный no-op (повтор после успешного восстановления либо единственный файл, уже названный `<файл-новый>`) — код 0 значит, что нужное имя файла есть на диске, и НЕ доказывает, что восстановление произошло; 1 — неверный вызов (usage), отказ подтверждения, файл не найден, ошибка ввода-вывода (включая сканирование архива), выбор старого файла (keep old) и имя, не являющееся парой после прерывания; 2 — номер не восстановим автоматически: больше двух файлов, расходящееся содержимое, одинаковые статусы (расходящаяся пара — это код 2, а не 1). Для automation код 2 у `recover` означает «сюда не лезь»: пара требует ручного разбора.

```bash
ticket set 7 done "починено"              # прерван посередине: код 2, оба файла в stderr
ticket recover 7 T-0007-done.md           # интерактивно: keep/discard + yes/no
ticket recover 7 T-0007-done.md --yes     # то же без вопроса, для automation
```

🔴 `recover` удаляет файл, поэтому проверять его только в песочнице: `-C /tmp/…` или `TICKETS_DIR`, никогда в боевом `tickets/`.

## Разовая миграция разметки (`normalize`)

Файлы в формате pre-MD022 (текущий формат без пустой строки до и после каждого заголовка) читаются, но обычный `ticket set` переписывал их лениво и дописывал журнальную строку «статус: X → X». `normalize` делает ту же перезапись один раз, не трогая журнал:

```bash
ticket normalize --dry-run      # напечатать пути, которые были бы переписаны, и ничего не писать
ticket normalize                # переписать их на месте
```

- Переписываются только файлы, байты которых отличаются от канонического рендера; имя файла не меняется, журнальная строка не добавляется.
- Имя файла авторитетно (V19): строка статуса в теле, расходящаяся с именем, рендерится в статус из имени — молча и без записи в журнал.
- Два guard'а пропускают файл с предупреждением в stderr и оставляют его байт в байт: bash-эровые метки, которые парсер не воспроизводит (`- Статус:`, в том числе с отступом, с маркером `*`/`+` и с пробелом перед двоеточием), и неполные метаданные (пустые type/priority/project, пустой заголовок, нулевая дата создания).
- `-P <проект>` ограничивает прогон одним проектом (точное совпадение, регистр важен). Дубликаты номеров печатаются так же, как у `list`: оба файла мигрируются, код выхода остаётся 0 — `normalize` никогда не возвращает 2.
- Удалённые тикеты нормализуются на месте так же: порядок обхода main → archive → deleted, нечитаемый или невалидный удалённый файл пропускается с тем же предупреждением, что и архивный, имя файла остаётся авторитетным. `--dry-run` ничего не пишет, включая удалённые файлы.
- `--dry-run` не берёт блокировку и не делает write-probe, поэтому работает и на каталоге `tickets/` только для чтения.

🔴 `normalize` переписывает файлы на месте: сначала прогоняйте на копии — `rm -rf /tmp/corpus && cp -r tickets /tmp/corpus && ticket -C /tmp/corpus normalize --dry-run`.

## Формат файла тикета

- Имя файла: `T-NNNN-<status>.md`; номер выдаётся атомарно через OS-локи и не переиспользуется.
- Статус хранится в имени файла. Вручную файлы не переименовывать: смену статуса делает `ticket set` (сам переименует файл и допишет журнал тикета).
- Жизненный цикл: `open` (новый) → `wip` (в работе) → `done` (исправлено) / `closed` (отклонён/дубликат). `deleted` терминален и read-only: назначает его только `ticket delete`, `set` (включая любой reopen) и `edit` тикета, чей файл лежит в `tickets/deleted/`, отказывают, обратной операции нет.
- Типы в заголовке: `BUG` — поломка; `OPS` — инцидент/обслуживание; `TD` — техдолг; `ENH` — улучшение.
- i18n: формат файла выбирается по `TICKET_LANG` в момент создания. Русская локаль даёт двуязычные метки (`## Summary (Кратко)`, `- Status (Статус): open`), английская — без перевода (`## Summary`, `- Status: open`). Файлы с чисто русскими заголовками (`## Кратко`, `- Статус:`) парсер не распознаёт: поля остаются пустыми, а ближайший `set` перезаписывает файл в текущем формате без них — такие файлы надо править вручную. Файлы формата pre-MD022 (текущий формат, но без пустой строки после заголовка) читаются и нормализуются при ближайшем `set`.
- `ticket new` без `-d` (или с пустым значением `Details`, например из пустого файла или stdin) вставляет в `Details` блок-формат — правило нумерованного списка: по одному пункту на строку, `N. <что> — <файл:строка>; <решение>`.
- Архив: `ticket archive` переносит закрытые тикеты в `tickets/archive/`; `list archive` смотрит архив; `show` и `set` работают с архивом, перевод архивного тикета в `open`/`wip` возвращает его в работу; `edit` правит архивный тикет на месте, без переноса.
- Удалённые: `ticket delete` переносит тикет в `tickets/deleted/T-NNNN-deleted.md` (тело, метаданные и журнал сохраняются, добавляется одна журнальная строка). Статус терминальный и read-only; показывает такие тикеты только `list deleted`, `archive` их игнорирует, номера не переиспользуются.
- Секреты (пароли, токены, ключи) в тикеты НЕ писать.

Пример тикета (`ticket new "Экспорт падает" -t BUG -p high -w ivan`, локаль RU):

```markdown
# T-0001 · BUG: Экспорт падает

- Status (Статус): open
- Priority (Приоритет): high
- Created (Создан): 2026-09-04 05:54 · by (кем): ivan
- Project (Проект): tmp

## Summary (Кратко)
Экспорт падает

## Details (Подробности)
<!-- Details = нумерованный список:
1. <что> — <файл:строка>; <решение>
-->

## User comments (Комментарии от пользователя)

## Comments (Комментарии)

## Journal (Журнал)
- 2026-09-04 05:54 — тикет создан (ivan).
```

## Секции

Секции: `Summary` — кратко; `Details` — подробности нумерованным списком, по одному пункту на строку: `N. <что> — <файл:строка>; <решение>` (файл:строка, логи, воспроизведение); `User comments` — пишет пользователь, агент читает перед работой над тикетом и туда не пишет; `Comments` — рабочие заметки агента, блок дописывается командой `ticket comment`; `Journal` — журнал, дописывается автоматически командами `new`/`set`/`edit`/`comment`/`section set`.
Интеграция с агентами, кросс-проектная работа, архив и жизненный цикл удаления в контексте: [scenarios.md](scenarios.md).
